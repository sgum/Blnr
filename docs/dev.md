## Оформление берём с portfolio.dtwin.ru, а не придумываем

Дизайн-система стенда — не авторская: токены, размеры карточек, структура
KPI, разметка подсказки и таблицы взяты с действующей витрины

**Чем это лечит.** Первая версия экрана была сделана «по вкусу», и оранжевый

шапкой страницы, 2px под заголовком карточки, заливка активной кнопки, тёплая
подсветка выбранной строки (`#ffefcc`). Красный и зелёный при этом остаются
только под рост и падение. Отказ от оранжевого делал стенд чужим среди
стендов компании — при том, что формально «ничего не нарушал».

## sprintf в R: строка формата не длиннее 8192 байт

**Симптом:** `'fmt' length exceeds maximal format length 8192` — экран не
собирается вообще.
**Причина:** весь CSS дашборда собирался одним `sprintf()`, и формат перерос
лимит R.
**Лечение:** палитра подставляется короткой `sprintf()`-строкой, правила идут
отдельным литералом и склеиваются `paste0()`. Побочная выгода — в литерале
проценты пишутся как есть, без удвоения `%%`, где легко ошибиться.
**Чем поймано:** гейтом сборки UI (`tests/test_functions.R`, раздел 6), а не
прогоном приложения.

## Всплывающая подсказка шириной 360px уезжает за край экрана

**Симптом:** подсказка у карточки в левой части экрана обрезана.
**Причина:** она центрируется по значку (`left:50%; translateX(-50%)`), и у
левого края уходит в отрицательные координаты (замерено: `x = −85`).
**Лечение:** как в оригинале — классы края `.ii.l` / `.ii.r`; в `info_tip()`
параметр `align` обязателен, умолчания «по центру» нет. Проверка требует,
чтобы ни один значок не остался с голым `class="ii"`.
**Чем поймано:** не глазами, а замером — `getBoundingClientRect()` по всем
подсказкам разом и проверкой `x < 0 || right > ширина окна`.

## В браузерной панели не работают ни :hover, ни :focus

Синтетический `hover` не выставляет CSS `:hover` (`el.matches(':hover')` →
`false`), а `el.focus()` делает элемент `document.activeElement`, но
`:focus` не матчится, потому что у окна нет системного фокуса. То есть
«подсказка не появилась на скриншоте» само по себе НЕ доказывает дефект.
Проверять принудительным показом (`tip.style.display='block'`) и замером
геометрии — так видно и то, что подсказка есть, и то, что она помещается.

## Проверка по HTML интерфейса: as.character(tag) теряет весь CSS

**Симптом:** тест «панель не обрезает всплывающую подсказку» отвечал «ok» и
на исправном коде, и на коде с заведомо возвращённым дефектом.
**Причина:** `as.character(dashboardUI())` рендерит только `renderTags(x)$html`.
Содержимое `tags$head(...)` htmltools выносит в ОТДЕЛЬНОЕ поле `$head`, и весь
инлайновый `<style>` экрана в строку не попадает. Проверка искала подстроку в
тексте, где её не могло быть ни при каких условиях, — то есть отвечала «нет
нарушений» на пустоте.
**Лечение:** склеивать оба поля:
`rt <- htmltools::renderTags(x); paste(as.character(rt$head), as.character(rt$html))`.
См. `flat()` в `tests/test_functions.R`, раздел 6.
**Урок общий (конституция, «мерь исправным прибором»):** проверка, введённая
взамен правила, сама обязана быть предъявлена входу, на котором она ОБЯЗАНА
покраснеть. Здесь негативный контроль и вскрыл, что прибор мерит пустоту;
без него в репозитории остался бы вечнозелёный тест.

## Всплывающая подсказка под «i» и overflow:hidden у карточки

**Симптом:** разметка и CSS подсказки верны, `data-tip` на месте, а по
наведению ничего не появляется.
**Причина:** подсказка — `position:absolute` внутри шапки карточки, а у самой

**Лечение:** `overflow` у `.panel` не задавать; прокрутку вешать на `.panel-body`.
Закреплено проверкой в `tests/test_functions.R`, раздел 6.
**Отдельно про прибор:** синтетический `hover` из браузерной панели НЕ выставляет
CSS `:hover` (`el.matches(':hover')` → `false`), поэтому «подсказка не
появилась на скриншоте» само по себе ничего не доказывает. Проверять, временно
продублировав правило `.itip:hover::after` на класс и навесив класс из JS.

## Форма входа без fluidPage()/bootstrapPage() — поля уже кнопки

**Симптом:** поля логина/пароля заметно уже кнопки «Войти», хотя в CSS у всех
одна и та же карточка-контейнер (поймано на скриншоте пользователя 24.09.2026).
**Причина:** `ui.R` строит шлюз авторизации через `tagList(...)` напрямую,
без `fluidPage()`/`bootstrapPage()` — а именно они подключают Bootstrap CSS.
Без него `class="form-control"` не значит НИЧЕГО: `<input>` — inline-block
элемент и сам не растягивается на ширину родителя. Кнопка была широкой
только потому, что `actionButton(..., width="100%")` пишет `width` инлайн-
стилем в обход Bootstrap — два элемента тянулись по разным механизмам,
поэтому совпадение их ширины было случайным, а не гарантированным.
**Лечение:** не полагаться на Bootstrap-классы без Bootstrap — либо
оборачивать поля в `display:flex; flex-direction:column` (тогда блочные дети
растягиваются по умолчанию, как в эталонном CSS `dt-auth-skill/references/
form.md`), либо явно `width:100%; box-sizing:border-box` на самих `<input>`.
**Более общий урок:** эталон навыка (`form.md`) даёт готовый HTML/CSS почти
построчно — пересказ своими словами тихо теряет то, что в оригинале держит
конструкцию (здесь — flex-контейнер). Копировать структуру ближе к тексту
эталона, а не реализовывать по памяти смысла.
**Чем поймано НЕ было:** моя собственная проверка перед деплоем сверяла
*наличие* элементов (лого, текст, ссылки — через `grep` по HTML и скриншот
с текстовыми маркерами), а не *пропорции*. Приёмка по чек-листу навыка
(`references/checklist.md`, пункт «Форма приведена к типовой») требует
сверки с эталоном, а не только присутствия кусков — визуальную сверку
пропорций/геометрии нужно делать явно, не только через список маркеров.

## curl не видит содержимое uiOutput() — только статику страницы

**Симптом:** проверка `curl ... | grep 'Вход в стенд'` не находит текст,
который явно есть на экране (браузером подтверждено).
**Причина:** `uiOutput()`/`renderUI()` — динамический вывод, заполняется
Shiny через websocket ПОСЛЕ того, как страница и JS уже загрузились. Голый
`curl` (без исполнения JS) видит только статичную обвязку `ui.R` (`<head>`,
инлайн `<style>` из `loginCSS()`) — совпадение текста CSS-класса
(`.dt-auth-card{...}`) с `grep`-паттерном может ложно выглядеть
подтверждением, хотя реального DOM `curl` не видел вообще.
**Лечение:** проверять рендер шлюза/дашборда только через браузер
(скриншот/`read_page`), не через `curl`+`grep`. `curl` годится только для
кода ответа/заголовков/сертификата/редиректов — не для содержимого
`uiOutput()`.

## Запуск приложения — только под UTF-8 локалью

**Симптом:** кириллица в интерфейсе рисуется как `<d0><93><d1>…` (сырые
UTF-8 байты).
**Причина:** R запущен с пустым `LANG`/локалью C (типично для headless
`Rscript`/cron). Исходники в UTF-8 при сборке UI мисэнкодятся.
**Лечение:** запускать под UTF-8 —
`LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 Rscript -e 'shiny::runApp()'`.
Из R.app/RStudio на macOS локаль уже UTF-8, поэтому там проблема не видна —
не обмануться «у меня же работает».
**Чем поймано:** скриншот запущенного приложения (не «должно работать»).

## global.R обязан грузить пакеты, используемые в UI

**Симптом:** `could not find function "setSliderColor"` при старте, белый экран
«An error has occurred».
**Причина:** `ui.R` сорсит `global.R` ПЕРВЫМ и там же строит UI, используя
`setSliderColor` (shinyWidgets), `useShinyjs` (shinyjs), `use_theme`/
`create_theme` (fresh). Эти `library()` стояли только в `server.R`, который
выполняется позже сборки UI.
**Лечение:** `library(shinyWidgets); library(shinyjs); library(fresh)` в
`global.R`. Общее правило: любой пакет, чьи функции зовутся при СБОРКЕ UI,
подключается в `global.R`, не только в `server.R`.

## forecast_for_date: имя аргумента не должно затенять столбец data.table

**Симптом:** прогноз на «сегодня» отдавал значение последнего шага (2028 г.),
а не нужной даты (в UI — абсурдные +25% «за неделю»).
**Причина:** `forecast_for_date(forecast, tkr, date)` фильтровал
`forecast[ticker == tkr & date <= as.Date(date)]`. Внутри `[.data.table` имя
`date` резолвится в СТОЛБЕЦ, поэтому `date <= as.Date(date)` истинно всегда.
**Лечение:** отдельное имя цели — `target <- as.Date(date); …date <= target`.
**Чем поймано:** прогон парсера с известными числами и сверка с UI-графиком.

## Шлюз авторизации: UI-функции нужны в ГЛОБАЛЬНОЙ области

**Симптом:** `could not find function "loginUI"` при рендере `output$gate`.
**Причина:** `output$gate` (server.R) строит `loginUI()`/`dashboardUI()`, а те
были `source(..., local = TRUE)` в `ui.R` — попадали в локальную область ui.R,

**Лечение:** UI-модули (`ui/*.R`) сорсить в `global.R` (без `local=TRUE`):

## bs4Dash rightUi требует класс 'dropdown'

**Симптом:** `Expected tag to have class 'dropdown'` при рендере дашборда.
**Причина:** `bs4DashNavbar(rightUi = tags$li(class="nav-item", ...))` — bs4Dash
валидирует, что элемент навбара имеет класс `dropdown`.
**Лечение:** `tags$li(class = "nav-item dropdown", ...)`.

## Данные не должны уходить до входа

Дашборд (`dashboardUI()`) создаётся только в `output$gate` ПОСЛЕ входа — до
этого его outputs не привязаны на клиенте и не считаются, поэтому позиции/цены
не отправляются в браузер неавторизованному. Не «прятать» дашборд CSS-ом поверх
данных: скрытый DOM всё равно приезжает клиенту.

## $0 и −100% вместо «нет данных» — ПОВТОР того же класса дефекта

**25.09.2026.** Стенд показал «Стоимость портфеля $0», «−$17 579»,
«−100.00%», пустые «Тек.» и «Стоимость» по всем бумагам. Портфель при этом
был цел: marketdata.app ответил **429 / «You've reached your API credit
limit»** на каждый запрос.

**Почему вышли именно нули, а не прочерки.** `summarize_portfolio()` считала
`sum(..., na.rm = TRUE)`. Этот аргумент превращает «неизвестно» в ноль:
сумма пустого набора равна 0, отсюда стоимость $0 и рост
`(0/entry − 1)·100 = −100%`. То есть витрина не промолчала, а уверенно
сообщила неправду — ровно тот класс, что уже описан выше про Yahoo. Запись
существовала и не удержала: **проверки на него не было**.

**Что сделано:**
* `na.rm` убран; нет цены хотя бы по одной позиции — итог `NA`, а `fmt_*`
  печатают прочерк. Гейт: `tests/test_functions.R`, раздел 6 (предъявлен
  входом с возвращённым `na.rm = TRUE` — три проверки краснеют).
* Источник обязан уметь сказать «нет данных»: `md_note_error()` /
  `md_status_text()` в `R/marketdata.R`, причина выводится плашкой в шапке
  («Нет котировок: исчерпан лимит кредитов marketdata.app»).

**Почему лимит кончился так быстро — два отдельных промаха:**
1. Кэш лежал в `data/md-cache` внутри рабочего каталога, а стадия деплоя
   делала `git clean -fdx` без исключения `data/`. Каждая выкатка стирала
   кэш (и заодно `data/portfolio_snapshots.csv` — то есть историю невязки,
   которая поэтому никогда бы не накопилась). Исправлено: `-e data/` в
   `jenkins/Jenkinsfile_broker_main`.
2. На каждую бумагу шло ДВА запроса — свечи и отдельная котировка
   `/quotes`. Теперь текущая цена — закрытие последней дневной свечи, и на
   инструмент приходится один запрос в сутки. В шапке честно написано, на
   какую дату закрытия показаны цены.

**Общий урок.** Заметка о классе дефекта не мешает повторить его в другом
месте — мешает только проверка. Проверка на «источник молчит» должна стоять
там же, где считается итог, а не только там, где данные читаются.

## Лимит источника определяет архитектуру: хранилище + ночная загрузка

**Факт (проверено 25.09.2026 заголовками ответа):** у аккаунта
marketdata.app `x-api-ratelimit-limit: 100` — сто запросов в сутки, сброс в
16:30 МСК. Это не «неудобство», а проектное ограничение: ползунок времени по
реестру наблюдения — сотни обращений на одно открытие экрана.

**Решение.** В API ходит ровно одно место — `scripts/fetch_marketdata.R`,
запускаемое заданием Jenkins раз в сутки (`jenkins/Jenkinsfile_marketdata` в
репозитории 311). Оно кладёт дневные ряды в локальное хранилище
(`R/store.R`, каталог `BLNR_STORE_DIR`), а стенд читает только оттуда:
`md_candles()` сначала смотрит хранилище, и без `BLNR_ALLOW_ONLINE=TRUE` в
сеть не пойдёт вовсе. Пустое хранилище даёт честное «нет данных», а не нули.

**Каталог хранилища обязан лежать ВНЕ рабочей копии.** Стадия деплоя делает
`git clean -fdx`; всё, что внутри репозитория и не в списке исключений,
стирается при каждой выкатке. Так уже сгорели кэш котировок и лог снимков.

**Четыре обязанности задания (конституция) и как они закрыты:**
1. прежняя версия — `store_rotate()` ДО записи, семь снимков в ротации;
2. падение на недоступном источнике — при отказе хотя бы по одному
   инструменту не пишется НИЧЕГО (частично собранное хранилище неотличимо от
   исправного);
3. проверка результата — `store_verify_series()`: глубина ряда, пустые
   закрытия, дубли и разнобой дат, устаревший хвост. Вынесена из скрипта в
   `R/store.R` именно чтобы её можно было предъявить плохому входу; тесты в
   разделе 7 делают это по каждому пункту;
4. история прогонов — в Jenkins.

**Замороженный ряд виден на экране.** Файлы на месте, числа правдоподобные,
просто даты кончились — и витрина показывает прошлое как настоящее (так стенд
200 два года показывал снимок 2024 года). Поэтому в шапке всегда написано, на
какую дату закрытия показаны цены, а при отставании больше пяти дней плашка
становится предупреждающей.

## Прибор: `$?` после конвейера — код ПОСЛЕДНЕЙ команды, а в zsh нет PIPESTATUS

Проверяя коды возврата загрузчика, я написал `Rscript ... | tail -5; echo $?`
и получил `0` у скрипта, который завершался `quit(status = 1L)`: `$?` вернул
код `tail`. Запасной вариант `${PIPESTATUS[0]}` тоже дал пустоту — это bash,
а оболочка здесь zsh (там массив называется `pipestatus` и индексируется с 1).
Вывод «отказная ветка не работает» был бы артефактом измерения.
**Как надо:** писать вывод в файл и читать `$?` сразу после команды.
