## Оформление берём с portfolio.dtwin.ru, а не придумываем

Дизайн-система стенда — не авторская: токены, размеры карточек, структура
KPI, разметка подсказки и таблицы взяты с действующей витрины

**Чем это лечит.** Первая версия экрана была сделана «по вкусу», и оранжевый

шапкой страницы, 2px под заголовком карточки, заливка активной кнопки, тёплая
подсветка выбранной строки (`#ffefcc`). Красный и зелёный при этом остаются
только под рост и падение. Отказ от оранжевого делал стенд чужим среди
стендов компании — при том, что формально «ничего не нарушал».

## sprintf в R: строка формата не длиннее 8192 байт

**Симптом:** `'fmt' length exceeds maximal format length 8192` — экран не
собирается вообще.
**Причина:** весь CSS дашборда собирался одним `sprintf()`, и формат перерос
лимит R.
**Лечение:** палитра подставляется короткой `sprintf()`-строкой, правила идут
отдельным литералом и склеиваются `paste0()`. Побочная выгода — в литерале
проценты пишутся как есть, без удвоения `%%`, где легко ошибиться.
**Чем поймано:** гейтом сборки UI (`tests/test_functions.R`, раздел 6), а не
прогоном приложения.

## Всплывающая подсказка шириной 360px уезжает за край экрана

**Симптом:** подсказка у карточки в левой части экрана обрезана.
**Причина:** она центрируется по значку (`left:50%; translateX(-50%)`), и у
левого края уходит в отрицательные координаты (замерено: `x = −85`).
**Лечение:** как в оригинале — классы края `.ii.l` / `.ii.r`; в `info_tip()`
параметр `align` обязателен, умолчания «по центру» нет. Проверка требует,
чтобы ни один значок не остался с голым `class="ii"`.
**Чем поймано:** не глазами, а замером — `getBoundingClientRect()` по всем
подсказкам разом и проверкой `x < 0 || right > ширина окна`.

## В браузерной панели не работают ни :hover, ни :focus

Синтетический `hover` не выставляет CSS `:hover` (`el.matches(':hover')` →
`false`), а `el.focus()` делает элемент `document.activeElement`, но
`:focus` не матчится, потому что у окна нет системного фокуса. То есть
«подсказка не появилась на скриншоте» само по себе НЕ доказывает дефект.
Проверять принудительным показом (`tip.style.display='block'`) и замером
геометрии — так видно и то, что подсказка есть, и то, что она помещается.

## Проверка по HTML интерфейса: as.character(tag) теряет весь CSS

**Симптом:** тест «панель не обрезает всплывающую подсказку» отвечал «ok» и
на исправном коде, и на коде с заведомо возвращённым дефектом.
**Причина:** `as.character(dashboardUI())` рендерит только `renderTags(x)$html`.
Содержимое `tags$head(...)` htmltools выносит в ОТДЕЛЬНОЕ поле `$head`, и весь
инлайновый `<style>` экрана в строку не попадает. Проверка искала подстроку в
тексте, где её не могло быть ни при каких условиях, — то есть отвечала «нет
нарушений» на пустоте.
**Лечение:** склеивать оба поля:
`rt <- htmltools::renderTags(x); paste(as.character(rt$head), as.character(rt$html))`.
См. `flat()` в `tests/test_functions.R`, раздел 6.
**Урок общий (конституция, «мерь исправным прибором»):** проверка, введённая
взамен правила, сама обязана быть предъявлена входу, на котором она ОБЯЗАНА
покраснеть. Здесь негативный контроль и вскрыл, что прибор мерит пустоту;
без него в репозитории остался бы вечнозелёный тест.

## Всплывающая подсказка под «i» и overflow:hidden у карточки

**Симптом:** разметка и CSS подсказки верны, `data-tip` на месте, а по
наведению ничего не появляется.
**Причина:** подсказка — `position:absolute` внутри шапки карточки, а у самой

**Лечение:** `overflow` у `.panel` не задавать; прокрутку вешать на `.panel-body`.
Закреплено проверкой в `tests/test_functions.R`, раздел 6.
**Отдельно про прибор:** синтетический `hover` из браузерной панели НЕ выставляет
CSS `:hover` (`el.matches(':hover')` → `false`), поэтому «подсказка не
появилась на скриншоте» само по себе ничего не доказывает. Проверять, временно
продублировав правило `.itip:hover::after` на класс и навесив класс из JS.

## Форма входа без fluidPage()/bootstrapPage() — поля уже кнопки

**Симптом:** поля логина/пароля заметно уже кнопки «Войти», хотя в CSS у всех
одна и та же карточка-контейнер (поймано на скриншоте пользователя 24.09.2026).
**Причина:** `ui.R` строит шлюз авторизации через `tagList(...)` напрямую,
без `fluidPage()`/`bootstrapPage()` — а именно они подключают Bootstrap CSS.
Без него `class="form-control"` не значит НИЧЕГО: `<input>` — inline-block
элемент и сам не растягивается на ширину родителя. Кнопка была широкой
только потому, что `actionButton(..., width="100%")` пишет `width` инлайн-
стилем в обход Bootstrap — два элемента тянулись по разным механизмам,
поэтому совпадение их ширины было случайным, а не гарантированным.
**Лечение:** не полагаться на Bootstrap-классы без Bootstrap — либо
оборачивать поля в `display:flex; flex-direction:column` (тогда блочные дети
растягиваются по умолчанию, как в эталонном CSS `dt-auth-skill/references/
form.md`), либо явно `width:100%; box-sizing:border-box` на самих `<input>`.
**Более общий урок:** эталон навыка (`form.md`) даёт готовый HTML/CSS почти
построчно — пересказ своими словами тихо теряет то, что в оригинале держит
конструкцию (здесь — flex-контейнер). Копировать структуру ближе к тексту
эталона, а не реализовывать по памяти смысла.
**Чем поймано НЕ было:** моя собственная проверка перед деплоем сверяла
*наличие* элементов (лого, текст, ссылки — через `grep` по HTML и скриншот
с текстовыми маркерами), а не *пропорции*. Приёмка по чек-листу навыка
(`references/checklist.md`, пункт «Форма приведена к типовой») требует
сверки с эталоном, а не только присутствия кусков — визуальную сверку
пропорций/геометрии нужно делать явно, не только через список маркеров.

## curl не видит содержимое uiOutput() — только статику страницы

**Симптом:** проверка `curl ... | grep 'Вход в стенд'` не находит текст,
который явно есть на экране (браузером подтверждено).
**Причина:** `uiOutput()`/`renderUI()` — динамический вывод, заполняется
Shiny через websocket ПОСЛЕ того, как страница и JS уже загрузились. Голый
`curl` (без исполнения JS) видит только статичную обвязку `ui.R` (`<head>`,
инлайн `<style>` из `loginCSS()`) — совпадение текста CSS-класса
(`.dt-auth-card{...}`) с `grep`-паттерном может ложно выглядеть
подтверждением, хотя реального DOM `curl` не видел вообще.
**Лечение:** проверять рендер шлюза/дашборда только через браузер
(скриншот/`read_page`), не через `curl`+`grep`. `curl` годится только для
кода ответа/заголовков/сертификата/редиректов — не для содержимого
`uiOutput()`.

## Запуск приложения — только под UTF-8 локалью

**Симптом:** кириллица в интерфейсе рисуется как `<d0><93><d1>…` (сырые
UTF-8 байты).
**Причина:** R запущен с пустым `LANG`/локалью C (типично для headless
`Rscript`/cron). Исходники в UTF-8 при сборке UI мисэнкодятся.
**Лечение:** запускать под UTF-8 —
`LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 Rscript -e 'shiny::runApp()'`.
Из R.app/RStudio на macOS локаль уже UTF-8, поэтому там проблема не видна —
не обмануться «у меня же работает».
**Чем поймано:** скриншот запущенного приложения (не «должно работать»).

## global.R обязан грузить пакеты, используемые в UI

**Симптом:** `could not find function "setSliderColor"` при старте, белый экран
«An error has occurred».
**Причина:** `ui.R` сорсит `global.R` ПЕРВЫМ и там же строит UI, используя
`setSliderColor` (shinyWidgets), `useShinyjs` (shinyjs), `use_theme`/
`create_theme` (fresh). Эти `library()` стояли только в `server.R`, который
выполняется позже сборки UI.
**Лечение:** `library(shinyWidgets); library(shinyjs); library(fresh)` в
`global.R`. Общее правило: любой пакет, чьи функции зовутся при СБОРКЕ UI,
подключается в `global.R`, не только в `server.R`.

## forecast_for_date: имя аргумента не должно затенять столбец data.table

**Симптом:** прогноз на «сегодня» отдавал значение последнего шага (2028 г.),
а не нужной даты (в UI — абсурдные +25% «за неделю»).
**Причина:** `forecast_for_date(forecast, tkr, date)` фильтровал
`forecast[ticker == tkr & date <= as.Date(date)]`. Внутри `[.data.table` имя
`date` резолвится в СТОЛБЕЦ, поэтому `date <= as.Date(date)` истинно всегда.
**Лечение:** отдельное имя цели — `target <- as.Date(date); …date <= target`.
**Чем поймано:** прогон парсера с известными числами и сверка с UI-графиком.

## Шлюз авторизации: UI-функции нужны в ГЛОБАЛЬНОЙ области

**Симптом:** `could not find function "loginUI"` при рендере `output$gate`.
**Причина:** `output$gate` (server.R) строит `loginUI()`/`dashboardUI()`, а те
были `source(..., local = TRUE)` в `ui.R` — попадали в локальную область ui.R,

**Лечение:** UI-модули (`ui/*.R`) сорсить в `global.R` (без `local=TRUE`):

## bs4Dash rightUi требует класс 'dropdown'

**Симптом:** `Expected tag to have class 'dropdown'` при рендере дашборда.
**Причина:** `bs4DashNavbar(rightUi = tags$li(class="nav-item", ...))` — bs4Dash
валидирует, что элемент навбара имеет класс `dropdown`.
**Лечение:** `tags$li(class = "nav-item dropdown", ...)`.

## Данные не должны уходить до входа

Дашборд (`dashboardUI()`) создаётся только в `output$gate` ПОСЛЕ входа — до
этого его outputs не привязаны на клиенте и не считаются, поэтому позиции/цены
не отправляются в браузер неавторизованному. Не «прятать» дашборд CSS-ом поверх
данных: скрытый DOM всё равно приезжает клиенту.

## $0 и −100% вместо «нет данных» — ПОВТОР того же класса дефекта

**25.09.2026.** Стенд показал «Стоимость портфеля $0», «−$17 579»,
«−100.00%», пустые «Тек.» и «Стоимость» по всем бумагам. Портфель при этом
был цел: marketdata.app ответил **429 / «You've reached your API credit
limit»** на каждый запрос.

**Почему вышли именно нули, а не прочерки.** `summarize_portfolio()` считала
`sum(..., na.rm = TRUE)`. Этот аргумент превращает «неизвестно» в ноль:
сумма пустого набора равна 0, отсюда стоимость $0 и рост
`(0/entry − 1)·100 = −100%`. То есть витрина не промолчала, а уверенно
сообщила неправду — ровно тот класс, что уже описан выше про Yahoo. Запись
существовала и не удержала: **проверки на него не было**.

**Что сделано:**
* `na.rm` убран; нет цены хотя бы по одной позиции — итог `NA`, а `fmt_*`
  печатают прочерк. Гейт: `tests/test_functions.R`, раздел 6 (предъявлен
  входом с возвращённым `na.rm = TRUE` — три проверки краснеют).
* Источник обязан уметь сказать «нет данных»: `md_note_error()` /
  `md_status_text()` в `R/marketdata.R`, причина выводится плашкой в шапке
  («Нет котировок: исчерпан лимит кредитов marketdata.app»).

**Почему лимит кончился так быстро — два отдельных промаха:**
1. Кэш лежал в `data/md-cache` внутри рабочего каталога, а стадия деплоя
   делала `git clean -fdx` без исключения `data/`. Каждая выкатка стирала
   кэш (и заодно `data/portfolio_snapshots.csv` — то есть историю невязки,
   которая поэтому никогда бы не накопилась). Исправлено: `-e data/` в
   `jenkins/Jenkinsfile_broker_main`.
2. На каждую бумагу шло ДВА запроса — свечи и отдельная котировка
   `/quotes`. Теперь текущая цена — закрытие последней дневной свечи, и на
   инструмент приходится один запрос в сутки. В шапке честно написано, на
   какую дату закрытия показаны цены.

**Общий урок.** Заметка о классе дефекта не мешает повторить его в другом
месте — мешает только проверка. Проверка на «источник молчит» должна стоять
там же, где считается итог, а не только там, где данные читаются.

## Лимит источника определяет архитектуру: хранилище + ночная загрузка

**Факт (проверено 25.09.2026 заголовками ответа):** у аккаунта
marketdata.app `x-api-ratelimit-limit: 100` — сто запросов в сутки, сброс в
16:30 МСК. Это не «неудобство», а проектное ограничение: ползунок времени по
реестру наблюдения — сотни обращений на одно открытие экрана.

**Решение.** В API ходит ровно одно место — `scripts/fetch_marketdata.R`,
запускаемое заданием Jenkins раз в сутки (`jenkins/Jenkinsfile_marketdata` в
репозитории 311). Оно кладёт дневные ряды в локальное хранилище
(`R/store.R`, каталог `BLNR_STORE_DIR`), а стенд читает только оттуда:
`md_candles()` сначала смотрит хранилище, и без `BLNR_ALLOW_ONLINE=TRUE` в
сеть не пойдёт вовсе. Пустое хранилище даёт честное «нет данных», а не нули.

**Каталог хранилища обязан лежать ВНЕ рабочей копии.** Стадия деплоя делает
`git clean -fdx`; всё, что внутри репозитория и не в списке исключений,
стирается при каждой выкатке. Так уже сгорели кэш котировок и лог снимков.

**Четыре обязанности задания (конституция) и как они закрыты:**
1. прежняя версия — `store_rotate()` ДО записи, семь снимков в ротации;
2. падение на недоступном источнике — при отказе хотя бы по одному
   инструменту не пишется НИЧЕГО (частично собранное хранилище неотличимо от
   исправного);
3. проверка результата — `store_verify_series()`: глубина ряда, пустые
   закрытия, дубли и разнобой дат, устаревший хвост. Вынесена из скрипта в
   `R/store.R` именно чтобы её можно было предъявить плохому входу; тесты в
   разделе 7 делают это по каждому пункту;
4. история прогонов — в Jenkins.

**Замороженный ряд виден на экране.** Файлы на месте, числа правдоподобные,
просто даты кончились — и витрина показывает прошлое как настоящее (так стенд
200 два года показывал снимок 2024 года). Поэтому в шапке всегда написано, на
какую дату закрытия показаны цены, а при отставании больше пяти дней плашка
становится предупреждающей.

## Ползунок времени: два дефекта, которых глазами не видно

Экран показывает портфель на выбранную торговую сессию. Здесь легко получить
картинку, которая выглядит совершенно правдоподобно и при этом неверна:

1. **Цена берётся последняя известная, а не на выбранную дату.** Портфель
   просто «не реагирует» на ползунок, но числа осмысленные, и заметить это
   можно только сверкой двух разных дат.
2. **Позиция считается существующей до даты покупки.** Тогда портфель «был»
   за полгода до того, как его купили: стоимость, рост и невязка считаются
   от цены входа, которой ещё не было.

Оба закрыты проверками (`tests/test_functions.R`, раздел 8) и оба предъявлены
входу, на котором краснеют: подмена `price_at` на последнюю цену и снятие
фильтра `quantity_at`.

**Ось времени — только реальные торговые сессии** из хранилища, причём
пересечение по всем бумагам (`store_sessions()`). На календарной шкале
половина делений — выходные, где цены нет; а если брать объединение дат,
портфель на некоторых сессиях считался бы по неполному набору бумаг.

**Снимок истории пишется только за фактическую дату.** Иначе прогулка
ползунком по прошлому переписывала бы накопленную историю задним числом.
По той же причине и график невязки, и прогнозная кривая на графике бумаги
обрезаются выбранной датой: на момент T будущего ещё не существовало.

## Кэш и состав портфеля — из реестра операций, а не из сводки

Сводка Exante (`/md/2.0/summary`) знает только СЕГОДНЯШНЕЕ состояние. С
ползунком времени этого мало: сегодняшний кэш рядом с прошлой стоимостью
бумаг даёт итог, которого никогда не существовало. Поэтому всё считается из
истории операций (`/md/2.0/transactions`, модуль `R/ledger.R`).

**Устройство ответа (проверено на боевом счёте 25.09.2026):**
* у сделки ДВЕ ноги с общим `orderId`: нога инструмента (`asset` = symbolId,
  `sum` = количество, `transactionPrice` = цена) и денежная (`asset` = "USD");
* комиссия — отдельная строка с тем же `orderId`;
* `valueDate` — дата зачисления; `when` — миллисекунды, не дата.

**Вход с известным ответом.** Реестр сверен со сводкой брокера: сумма всех
денежных ног = остаток до цента (28 019.83), количества совпали по всем семи
позициям, средние цены — по всем семи. Сверка не разовая: `ledger_reconcile()`
гоняет её при каждом чтении, расхождение выводится на экран. Реестр, тихо
разошедшийся с брокером, — худший исход: числа остаются правдоподобными.

**Три ловушки, каждая закрыта проверкой:**
1. **Валютные конвертации выглядят как позиции.** `AUTOCONVERSION` приходит
   теми же транзакциями с `asset` = "EUR" / "EUR/USD", и без фильтра в
   портфеле появляется «бумага» на 3990 штук. Признак бумаги — суффикс биржи
   через точку; у валют его нет.
2. **Комиссия в среднюю цену входить не должна.** Exante считает
   `averagePrice` без неё, и наша цена расходилась ровно на комиссию — это
   читалось бы как ошибка реестра. Комиссии полностью учтены в кэше.
3. **Опцион нельзя сводить к базовому тикеру.** `AMD.CBOE.20G2026.C220` при
   наивном `sub("\\..*$")` превращается в `AMD`, опционная позиция молча
   сливается с акционной и оценивается по цене акции. На счёте владельца
   опционы торгуются, так что случай не гипотетический: у опциона symbolId из
   четырёх частей, и он остаётся отдельной позицией.

**Зашитый список `portfolio_holdings` расходится с реальностью.** Сверка
25.09 показала: в истории счёта нет покупки от 14.09 вовсе, текущий портфель
куплен 24.09, и состав другой (GS 1 вместо 5, плюс IBM и INTC, GOOGL вместо
GOOG). Список остаётся только резервом на случай, когда кред нет, и помечен
на экране как «Позиции: вручную».

**GOOGL и GOOG — разные бумаги.** Счёт держит класс A (GOOGL.NASDAQ), а в
модельном воркбуке строка «Google» одна и сопоставлена с GOOG. Подменять одну
другой нельзя: цены разные. Прогноз по GOOGL остаётся пустым.

## Сравнение с моделью: только за период владения

**Дефект (26.09.2026).** Плитка «Портфель против модели» показывала **+7.71 пп**
при фактическом результате портфеля **+0.79%**. Причина: прогноз накоплен от
базовой даты файла (11.09), а шесть позиций из семи открыты 24.09. Сравнение
«от базы» приписывало портфелю движение цены за время, когда бумаг ещё не
было: по INTC «от 11.09 +23.75%», Δ +21.79 пп — при нулевом сроке владения.

**Лечение.** `forecast_between()` приводит накопленный прогноз к дате входа:
`(1+f(T))/(1+f(T0)) − 1`. Вход раньше базы — считаем от базы, раньше неё
модели просто нет. Столбец «от базы» остался в таблице как характеристика
БУМАГИ, но портфель по нему не судят.

**Проверка** (раздел 10) предъявлена входу, на котором краснеет: та же бумага
с двумя датами входа даёт разные ожидания, и `dev_pct` ≠ `dev_since_entry_pp`.

**Смежный дефект, который это вскрыло:** дата покупки бралась как первая
сделка по бумаге вообще. AMD показывала 737 дней владения, хотя прежний лот
был распродан в 2025-м, а текущий куплен 24.09. Теперь позиция помнит и дату
открытия текущего лота (`opened_date`), и первую сделку (`first_date`).

## Динамика счёта: тихое занижение и почему не стопка областей

**Занижение.** Стоимость бумаг считалась только по инструментам, для которых
есть ряд цен, а остальные молча пропускались. В истории счёта 32 инструмента
из 45 — опционы, рядов на них на текущем тарифе нет. Линия оставалась гладкой
и заниженной. Теперь сессия, где держится неоценимый инструмент, даёт `NA` —
на графике разрыв, а список таких инструментов выводится под «i».

**Почему не области с накоплением.** Стопка читалась бы лучше, но кэш на этом
счёте уходит в минус (маржа, на истории до −$19 925), а стопка с отрицательной
составляющей рисует неправду: верхняя граница перестаёт быть итогом. Оставлены
линии плюс нулевая отметка.

**Окно.** 150 сессий мало: счёт может простоять в деньгах весь отрезок, и
график выглядит пустым при живой истории. Переключатель «вся история» / «окно
шкалы» в шапке карточки; глубина «всей истории» ограничена хранилищем рядов.

## Право торговать проверяется на сервере, а не скрытием кнопки

Вход на стенд и право распоряжаться счётом — разные вещи. Смотреть портфель
может каждый из `BLNR_ALLOWED_USERS`, отправлять поручения — только владелец
(`BLNR_TRADERS`, по умолчанию `s.gumerov`).

**Почему проверка стоит в обработчике, а не только в разметке.** Скрытая
кнопка — это не право: событие Shiny подделывается из консоли браузера одной
строкой. Проверено на живом стенде под `v.alad`:

```js
Shiny.setInputValue('trade_open','sell|GS',{priority:'event'})
Shiny.setInputValue('trade_confirm',1,{priority:'event'})
```

Окно не открылось, обработчик отказал («Распоряжаться счётом может только его
владелец»), отказ лёг и в журнал поручений, и в лог приложения. Если бы
защитой было только отсутствие кнопки, поручение ушло бы на боевой счёт.

**Право торговать не шире права входа:** `user_can_trade()` требует членства
в обоих списках, иначе строка в `BLNR_TRADERS` давала бы доступ в обход
белого списка стенда.

## Отправка поручения отделена от его сборки

`exante_place_order()` без `apply = TRUE` не делает НИ ОДНОГО сетевого вызова:
возвращает тело запроса и всё. `apply = TRUE` выставляется ровно в одном
месте — обработчике `input$trade_confirm`, то есть по нажатию в окне, где
показано, что именно уйдёт. Ни реактив, ни таймер, ни стартовый `observe` не
имеют права его звать.

Проверки валидации живут В САМОЙ функции, а не только в интерфейсе: сторона
сделки, положительность и числовой тип количества. Интерфейс может измениться,
а деньги настоящие.

**Биржевой код не угадывается.** `GS.NYSE` и `GS.NASDAQ` — разные инструменты,
и поручение ушло бы не туда. Код берётся из позиций счёта или истории
операций; бумаги там нет — кнопка объясняет почему, а не подставляет суффикс.
Опцион при этом не выдаётся за акцию (см. `exante_is_option`).

**Журнал поручений** (`store/orders.csv`) пишется при каждой попытке, включая
отказ по праву: реестр операций Exante обновляется раз в сутки, и без журнала
вопрос «нажимал или нет» не разрешается ничем.

## Наблюдение и справочник — это ДВА РАЗНЫХ понятия, а не одно

**Поймано владельцем 26.09.2026:** «со справочником ты намудрил». Одна кнопка
«×» делала вид, что делает одно дело, а делала два несовместимых.

Как было: список наблюдения лежал в хранилище целиком, и крестик выкидывал из
него любую строку — включая бумаги из рабочей таблицы. После этого инструмент
исчезал из стенда насовсем, а строка прогнозной модели по нему оставалась
висеть без тикера: сопоставление идёт по `name_model` из реестра, а реестра
больше нет. Вернуть бумагу можно было только набрав тикер заново и уже без
строки модели.

Как надо, и почему именно так:

* **Наблюдаемые бумаги** — исходный состав из рабочей таблицы (`WATCHLIST` в
  `R/watchlist.R`). По ним есть прогнозная модель и история сделок, поэтому их
  можно только **выключить из мониторинга**: флаг `active`, действие обратимо,
  строка остаётся в реестре вместе с `name_model`.
* **Глобальный справочник** — всё, что вообще можно взять на счёт (биржевые
  списки Exante). Это источник НОВЫХ бумаг: оттуда инструмент, которого у
  стенда до сих пор не было, добавляется в наблюдение. Добавленное вручную
  помечается `source = "added"` и вот его удалять можно — оно взято по ошибке
  или больше не нужно.

Отсюда устройство хранилища: `watchlist.csv` держит не список, а **состояние**
по тикеру. Исходный набор всегда берётся из кода и накладывается состоянием из
файла — так растущий seed не теряется (файл, записанный до его пополнения, о
новых бумагах не знает), а подписи и `name_model` не морозятся старым CSV.

Два края, где это ломается молча:

* **отсутствие флага `active` в старом файле надо читать как «включено».**
  Прочитать как «выключено» значило бы снять мониторинг целиком одной
  выкаткой, и стенд выглядел бы пустым без единой ошибки. То же для `NA`.
* **незнакомая строка из старого файла — «добавлена вручную», но seed-бумага
  из него — нет.** Иначе `AAPL`, попавший в старый файл, стал бы удаляемым.

Ряд цен не удаляется ни при выключении, ни при удалении: он нужен истории
портфеля, если бумага когда-то покупалась. Бумагу, которая сейчас в портфеле,
выключить нельзя — её нечем было бы оценить. Последний включённый выключить
нельзя: пустой мониторинг — сломанный стенд.

Перед добавлением тикер проверяется у ИСТОЧНИКА ЦЕН одним запросом. Справочник
Exante и marketdata.app — разные источники: бумага, доступная к покупке, может
не иметь рядов, а реестр с такой бумагой ронял бы ночную загрузку каждую ночь
(она «всё или ничего»).

Справочник тянется **отдельным заданием** (`jenkins/Jenkinsfile_catalog`, раз в
неделю): состав листингов меняется раз в недели, а цены — каждый торговый день.
Путь выгрузки — `/md/3.0/exchanges/<биржа>`; вариант `.../symbols` отвечает 404
(проверено 26.09.2026 на живом контуре).

## Красный прогон тестов в локали C — дефект прибора, а не продукта

**26.09.2026.** `Rscript tests/test_functions.R` упал на выгрузке в Excel:
`Sheet 'Реестр' does not exist` — сразу после `addWorksheet(wb, "Реестр")`.
Выглядело как сломанная выгрузка. Выгрузка была исправна: в macOS `Rscript`
запускается с `LC_CTYPE=C`, и кириллица в имени листа калечится между
созданием и обращением. В `LC_ALL=ru_RU.UTF-8` те же тесты зелёные.

Первое, что я сделал правильно, — проверил, падает ли это ДО моих правок
(падало). Иначе разбирал бы собственный код в поисках дефекта, которого в нём
нет: ровно тот класс ошибки, что и «чтение карты репозитория в локали C».

## Процент прячет масштаб: результат портфеля показываем деньгами

**Поймано владельцем 26.09.2026.** На панели «портфель против модели» факт
падал на 30%. Это была ОДНА акция IBM за $285, подешевевшая на 20%, — при
$45 тысячах на счёте. Процент считался от вложенного в бумаги, а подпись
говорила «портфель», и разница в масштабе исчезала.

Та же ловушка повторилась в плитке KPI: когда сравнение привязали к сроку
владения, единственной позицией с ненулевым сроком остался тот же IBM, и его
−20% снова выдавали себя за результат портфеля.

**Лечение — деньги.** −$60 остаются −$60 рядом с $45 699 итога, подменить
масштаб нечем. Плитка дополнительно пишет охват: «по 1 из 7 позиций».
Процентные колонки из ряда невязки убраны совсем, чтобы к ним не вернулись.

**Правило:** доля показывается процентом только тогда, когда знаменатель
очевиден из подписи. «Портфель −20%» при знаменателе «вложено в бумаги» —
не подпись, а ловушка.

## Ноль — это утверждение. Нечего сказать — ставь прочерк

Столбец «Модель» был полон `+0.00%`: позиции куплены в день просмотра, срок
владения нулевой. Формула честно давала ноль, и читалось это как «модель
обещала топтание на месте», хотя она не обещала ничего.

`forecast_between()` теперь возвращает `NA` при нулевом сроке, а рядом с датой
покупки выводится срок владения — видно, ПОЧЕМУ прочерк. Тот же приём, что и
с ценами: `na.rm = TRUE` превращал «неизвестно» в ноль, здесь ноль возникал из
арифметики. Источник разный, вывод один.

## База прогноза берётся из ФАЙЛА, а не из глобальной константы

`forecast_between()` ограничивал начало периода константой
`FORECAST_BASELINE_DATE`. У каждого модельного воркбука своя база, и константа
делала вид, что знает чужую: прогноз, начинающийся в июне, обрезался
сентябрьской константой и молча становился `NA`. Теперь начало берётся как
`min(forecast$date)` по этой бумаге. Поймано тестом на синтетике, а не на
проде.

## Ноль в подписи читается как сбой — пиши словами

## Ночная загрузка читала собственное хранилище и была пустышкой

**Самый дорогой дефект этой работы.** `md_candles()` проверял хранилище
ПЕРВЫМ и безусловно:

```r
st <- store_read_candles(ticker)
if (nrow(st) > 0) return(utils::tail(st, days))   # даже при online = TRUE
```

Загрузчик вызывал ту же функцию и получал обратно файл, который собирался
переписать. После первого успешного прогона ночная загрузка перестала
обновлять что-либо — и при этом:

* отчитывалась `SUCCESS`;
* печатала «Готово: 24 инструментов, 9600 строк» (данные из хранилища);
* проходила стадию `Verify on store` — та сверяет число инструментов и
  свежесть в пять дней, а отставание на один день штатно для выходных.

Ряды стояли на месте с 25.09 по 26.09.2026. Поймал это не пайплайн, а
владелец: заметил «0 дн» у позиции, купленной два дня назад.

**Лечение:** `online = FALSE` (стенд) читает ТОЛЬКО хранилище, `online = TRUE`
(загрузчик) идёт ТОЛЬКО в API. Проверка в разделе 7 подменяет `md_get` и
требует, чтобы при `online = TRUE` вернулись данные источника, а не файла;
на возвращённом дефекте краснеет.

**Урок про проверки.** `Verify on store` проверял ЧИСЛО инструментов и
свежесть — то есть форму, а не факт обновления. Проверка результата обязана
отвечать на вопрос «стало ли новее», а не «похоже ли на правду». Сверять
`last_date` до и после прогона.

## Запоминание входа: подписанная кука, а не сессия в памяти

Человек, однажды набравший пароль, не набирает его при каждом обновлении
страницы. Реализовано кукой с HMAC-SHA256 на серверном секрете: внутри логин,
срок и подпись.

**Почему не хранилище сессий в памяти процесса.** Воркер Shiny перезапускается
при каждой выкатке и по простою (`app_idle_timeout`), и всё, что лежало в его
памяти, умирает вместе с ним — человек снова у формы, то есть ровно та беда,
ради которой всё затевалось. Подписанная кука переживает и перезапуск, и
перевыкатку.

**Кука удостоверяет ТОЛЬКО личность.** Право входа (белый список) и право
торговать (`BLNR_TRADERS`) проверяются заново при каждом восстановлении и при
каждом действии: человека могли убрать из списка, пока кука жила. Восстановление
для исключённого пользователя гасит куку и пишет отказ в журнал.

**Секрет короче 32 символов или отсутствует — запоминание выключено целиком.**
Отказ в безопасную сторону: подпись на пустом или коротком ключе подделывается.

**Secure только по https.** На http браузер молча не сохранит куку с этим
флагом, и запоминание «не работает» без единого сообщения — поэтому флаг
добавляется из JS по `location.protocol`.

**Почему не HttpOnly.** Куку ставит браузер из JS: Shiny отдаёт страницу по
вебсокету и заголовками ответа не распоряжается. Плата — кука видна скриптам
страницы. Риск ограничен тем, что стенд не отображает пользовательский ввод;
если начнёт — куку надо переносить на nginx.

**Выход гасит куку ДО перезагрузки.** Иначе восстановление на старте новой
сессии тут же вернёт человека внутрь, и «Выйти» перестанет работать.

**Прибор:** проверяя выход, я нажал `.hdr a` — и это оказалась кнопка выгрузки
в Excel, а не «Выйти»: в шапке два элемента `<a>`, и первый — downloadButton.
Вывод «выход не работает» был артефактом. Искать элемент по его действию
(`onclick` содержит `auth_logout`), а не по позиции в разметке.

## Деплой оставлял стенд без HTTPS при любом своём отказе

**26.09.2026, сборка 33.** `broker.dtwin.ru` перестал отвечать: `curl` —
ошибка TLS, браузер — предупреждение о подмене. Другие домены работали.
Причина: в `sites-enabled` лежал симлинк на `broker.dtwin.ru.conf.bootstrap` —
временный HTTP-only конфиг для ACME. Он не слушает 443, поэтому SNI уходил в
дефолтный сервер и отдавал сертификат соседнего домена (`CN=207api.dtwin.ru`).

**Как до этого дошло.** Пайплайн подменял рабочий vhost на bootstrap НА КАЖДОЙ
выкатке, до получения сертификата. Стадия сертификата упала на
`Another instance of Certbot is already running` — общий lock отняла соседняя
выкатка, — и все последующие стадии, включая возврат рабочего конфига, были
пропущены. Отказ ДЕПЛОЯ превратился в отказ СТЕНДА.

**Три правки:**
1. bootstrap ставится ТОЛЬКО когда сертификата ещё нет; при живом сертификате
   рабочий vhost не трогается вовсе, и окно отказа исчезает;
2. certbot повторяется пять раз с паузой — lock освобождается за минуты, а
   одиночная попытка роняла весь деплой, хотя делать было нечего;
3. `post { failure }` возвращает рабочий симлинк, если сертификат и конфиг на
   месте: неудачный деплой не должен оставлять стенд лежать.

**Чем поймано.** Не пайплайном: он отчитался FAILURE, но никто не связал это с
недоступностью стенда. Поймал `curl`, давший exit 60 вместо кода ответа, —
я сначала списал это на переходный эффект reload, и это было неверно: exit 60
держался три попытки подряд. Ошибка TLS, повторяющаяся подряд, — не шум.
